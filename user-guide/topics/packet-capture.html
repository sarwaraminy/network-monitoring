User Guide

Packet capture

Live packets from one adapter, decoded frame by frame.

Starting a capture

  1. Choose a Network interface. The list comes from the capture driver on the server, not from your own machine.
  2. Leave Snapshot length and Timeout as they are unless you have a reason:
    • Snapshot length is how many bytes of each frame to keep. The default of 65536 keeps whole frames; lowering it truncates payloads and can hide what a detector needs to see.
    • Timeout is the pcap read timeout in milliseconds.
  3. Click Start capture. The status chip changes from Idle, and decoded packets appear newest-first as they arrive.
  4. Stop ends the session. Clear empties the table without stopping.

Capture by IP is the same screen with an address filter, for when you already know which host you are interested in.

Capture does not survive a restart

A capture runs until you stop it — the Timeout above is how long the driver waits before handing over a batch of packets, not how long the capture lasts. But it lives only in the running service, so restarting it, rebooting the machine or redeploying the container all end the capture.

Flow collection is different: if your switches export NetFlow or IPFIX, that comes back on its own when the service starts. Only packet capture needs somebody to start it.

The screen tells you when that has happened. Instead of the bare Idle chip — which would look the same as a machine that has never captured anything — a banner names the interface, when it started and — if you are an administrator — who started it, with a Resume button that runs it again on the same settings.

The banner stays until you start a capture. It does not come back after that, and it does not come back on the next restart either: the notice belongs to the run that found it, so a service restarted twice does not report the same interruption twice.

An installation that would rather not wait to be told can have the service resume by itself, by setting CAPTURE_RESUME_ON_START=true where the server is configured. It is off by default and there is deliberately no switch for it in the interface: capture reads other people’s traffic, and starting it with nobody present is a decision for whoever installed the server. It only ever resumes a capture somebody explicitly started, on the interface they named.

What you will actually see

A capture only sees the traffic that reaches the machine it runs on. On an ordinary workstation that is its own traffic plus broadcasts — enough for ARP and new-device detection, and not much else. Seeing a whole segment needs the switch configured to mirror traffic to this machine (a SPAN port) or a network TAP.

Note

Detection does not depend on this screen. Findings are raised from whatever traffic the server is processing, whether or not anybody has a capture open in a browser, and a flow collector feeds detection with no capture at all.

Who can use this

Any signed-in account can view the interfaces and the packets already captured. Starting, stopping and clearing a capture are restricted to administrators — a capture puts an interface into promiscuous mode and reads other people's traffic, which is not something every account should be able to begin.
