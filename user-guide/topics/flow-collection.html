Flow collection

What your routers and switches are telling you, and whether any of it can be read.

Flow collection is the other way this tool sees the network, and for most installations it is the more useful one. Packet capture needs a driver on this host and a mirror port on a managed switch to see anything beyond its own traffic; flow needs neither. The devices you already own do the observing and send summaries here — one record per conversation, with the addresses, ports, byte counts and TCP flags, but not the contents.

Less detail per connection, then, and vastly more of the network.

What this screen is for

Setting flow up goes wrong in a small number of specific ways, and they look identical if all you have is a count. This screen names whichever one applies instead:

What it saysWhat it means
Listening, and nothing has arrived yet The socket is open and no datagram has reached it. Either the device is not sending, it cannot reach this host, or it is sending somewhere else. Check the exporter's destination address and anything between it and here that filters UDP.
Every record is waiting for a template The sharp one, and the reason this screen exists. NetFlow v9 and IPFIX do not describe their own records — the layout arrives separately, on its own interval — so records that turn up first are counted and cannot be read. The device looks busy and contributes nothing. It usually clears within a few minutes; if it does not, shorten the template refresh interval on the exporter.
The socket is not open Collection is switched on and the bind failed. Either another process holds the port, or FLOW_BIND_ADDRESS names an address that is not on this host. Nothing is being received. The API log says which.
Datagrams discarded Arrived and were dropped before being read, broken down by cause — see below.
Collecting Records are being decoded and inspected. The counters are the detail.
On and listening are two different things

The chip at the top right says Listening on 0.0.0.0:2055 rather than just "on", and that is deliberate: being configured to listen and having actually opened the socket are separate facts, and they come apart exactly when the bind fails. A single on/off would hide the second most likely setup failure behind the most likely one.

Why a datagram was discarded

Three unrelated things used to be counted under one number. They are listed separately because each is fixed somewhere else:

  • Sender not permitted. The address is not in the permitted list, so nothing from it is read. Administrators see the list printed underneath — comparing your device's address against it is usually the whole diagnosis — and everyone else sees how many senders are permitted, which is enough to read the refusal count. Flow has no authentication at all, so this list is the only access control there is, which is why the addresses themselves are not shown to everyone: they are a precise description of what somebody would have to impersonate.
  • sFlow. A different protocol that happens to share the port and the version number. It is recognised and refused rather than mis-read as NetFlow. Reconfigure the device for NetFlow or IPFIX.
  • Version not implemented. NetFlow v5, NetFlow v9 and IPFIX are the three this tool reads. The version number is shown so you can take it to the device's configuration.

Reading the exporter table

One row per device, busiest first — on a real network one device dominates, and that is the one worth looking at. Awaiting template is the column to watch: any number other than zero there means that device is sending records this tool cannot yet read, and a device with records at zero and this climbing is the case described above.

On Docker Compose, the port needs a second file

The UDP port is published by docker-compose.flow.yml, not by the main Compose file — putting it there would open it on every deployment, including ones that never wanted flow. Without that override the collector binds inside the container, reports itself listening quite correctly, and receives nothing, because nothing forwards the port to it.

Every counter on this screen then reads exactly like a device that is not sending, which is why the warning is on the page rather than only in the documentation. Start the stack with both files:

docker compose -f docker-compose.yml -f docker-compose.flow.yml up -d

Switching it on

Flow collection is off until somebody asks for it. When it is off, this screen tells you how to switch it on rather than showing an empty set of counters — a page reading "0 datagrams" is indistinguishable from a broken one.

Use the form, not the file

That panel offers two routes and puts them in this order deliberately. The settings form is the one to use. Setting these in api/.env also works — a deployment that keeps its configuration in files is entitled to that, and a value there wins — but it then disables that field in the form, and the only way to change the setting afterwards is to edit the file again and restart.

That is worth knowing before you paste anything: the file route quietly costs you the browser route for every field you use it on.

An administrator changes these from Administration settings → Flow collection settings, with no file to edit and no restart. A setting present in the server's own configuration wins and is shown disabled there, with the variable named, for the reason every setting in this product follows that rule: a deployment that keeps its configuration in a file is meant to keep that guarantee.

Switching it off again on Docker

On Docker, collection is on because you started the stack with the flow override file. Stop starting it with that file and collection stops — the switch goes back to off, and the published port goes with it. That is the intended way to turn the feature off on a Compose deployment.

The port, the bind address and the permitted senders behave the other way round: the first start copies them into the settings so that removing the file later keeps the configuration you had, ready for you to switch collection back on from the form. The on/off switch is deliberately not copied, so that removing the file cannot leave a collector running on a setting from a file you deleted.

The four settings are not equal

Only one of them is purely this application's business, and the form separates them for that reason:

  • Permitted senders is checked against each arriving datagram, so it takes effect the moment you save it. Nothing is interrupted. This is the one that changes in ordinary use, as devices are added — and since NetFlow has no authentication at all, it is the only access control there is.
  • The switch, the port and the bind address describe a socket that is already open, so saving any of them closes it and opens a new one. A few seconds of traffic is not collected. The form says which group you are editing.
A save can succeed and still not take effect

If the new port is already in use, or the bind address is not an address on this machine, the socket cannot be reopened. The setting is saved — it is what the next restart will use — but nothing is being collected right now, and the form says so rather than showing a tick. This screen is the live answer: it is one click away under Capture, and it is where the collector's state is reported. The settings window is for changing things, not for reading them.

If the collector was already stalled when you opened the settings — a port that was busy when the server started, freed since — every value in the form is already correct, so there is nothing to save. A Try binding again button appears in that case and reopens the socket without changing anything.

On Docker, the port is not this form's to change

The port your devices send to is published by the Compose file, which this application cannot see. Changing the port here moves the socket inside the container while Docker goes on forwarding the old one, so collection stops — and every counter then reads exactly like a device that has stopped sending. Change it for the whole stack and redeploy instead.

On the flow Compose override the port and the bind address are fixed for you, so the field is disabled and the mistake is out of reach.

Who can use this

Everyone who can sign in. Whether the collector is listening is not privileged information, and this screen changes nothing — the operator watching the network is usually not the administrator. Changing the settings is an administrator's job and lives under the gear.

One detail on the page is administrator-only: the addresses in the permitted list. Everyone sees how many there are.
